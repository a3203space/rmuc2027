# 观测是否包含「对手底盘形态」识别

> **状态（2026-11-22）**：`OBS_VERSION` = **2**、`OBS_SIZE` = **131**，敌方每槽新增三个能力位。这三个位**不是**查静态机型表得来的，而是 `terrain_witness.py` 从**我方视野内观察到的行为**推断：对手踩到了隧道内侧卡、或量到了 200mm 台阶的两次抬升。原始审计过程保留在 §二～§四作为依据。

## 结论

**已编码，但按「观察到的行为」编码，不按「机型查表」、也不按 `chassis_type`。** 雷达只给坐标，所以能力只能被看见，不能被查询。三个位里隧道和台阶两位是实证推断，全向位留零——横向漂移在坐标轨迹里不留痕迹。

## 一、为什么必须是「观察」，不能是「查表」

用户最初的思路是：**用雷达拿到的连续坐标轨迹，判断对方能否过洞 / 上台阶 / 都不能，再把它映到观测维度上。** 这条路是对的，而且比查机型表更贴合真实比赛。

官方口径逐条核对过：

| 想知道的 | 官方有没有下发 | 出处 |
|---|---|---|
| 对手坐标 | 有 | 协议 p.67 `RadarInfoToClient`：`uint32 x(cm)`、`uint32 y(cm)`、`uint32 特殊标识` |
| 底盘构型 | **没有** | 协议 p.13 表 1-12 `0x0201 robot_status_t` 字段止于 `power_management_shooter_output` |
| 是否轮足 | **没有** | 同上；雷达报文只有 x/y/特殊标识三样 |

`RadarInfoToClient` 完整定义（协议 p.67）：

```
message RadarInfoToClient {
    repeated uint32 RadarSingleRobotInfo;   // 按 对方 1,3,4,7;己方 1,3,4,7 顺序
}
// 每个机器人 3 个 uint32：位置 x（cm）、位置 y（cm）、是否特殊标识
// 特殊标识：0=否；1=是；2=是但该机器人定位模块离线
```

规则 p.111-112 §5.7.4 也只写「雷达可识别双方地面机器人的**位置**」，识别误差分 准确(<0.8m) / 半准确(<1.6m) / 错误(≥1.6m)。**整份协议没有任何字段能告诉你想知道的那件事**，所以能力位只能靠推断。

### 规则里的「底盘类型」是功率档位，不是构型

规则 p.91 表 5-17 的「底盘类型」只有两个取值：**功率优先** / **血量优先**，配的是上限血量与底盘功率（150 血 60W … 400 血 100W）。这是赛前 3 分钟选的**性能配点**（p.91 原文：「步兵机器人的操作手可选择机器人的底盘和发射机构类型」），不是麦轮/轮足/全向。照字面编码会得到「它点了功率还是点了血量」，和能不能过洞无关。

物理构型只在《机器人制作规范手册》p.42-43 的「充分再设计」里被列举（麦轮、舵轮、全向轮、阿克曼、履带），同处 p.43 另有「足式机器人的关节电机……不计入底盘功率」。**手册从未给出封闭的三分类**，也不存在能照抄的官方枚举。

## 二、两个地形能力位：为什么是这两个，怎么观测

### 隧道：踩到内侧卡就是铁证

规则 p.106 表 5-27「隧道增益触发逻辑与效果」把过隧道分成两种：

| 增益类型 | 场地交互模块卡检测顺序 | 效果 |
|---|---|---|
| 地形跨越增益（**跨越**隧道） | 仅隧道一端 + 另一端 | **25% 防御，30 秒** |
| 地形跨越增益（**穿越**隧道） | 隧道一端 + **内部** + 另一端 | **1.5 倍热量冷却，120 秒** |

p.105 说明两者「相互独立」；p.106 又规定持有一种后再拿另一种会升级为 **50% 防御**并按较长剩余时间更新。**能钻进顶棚下拿到 1.5× 冷却（120s）的对手，和只能从上面跨过拿 25% 防御（30s）的，是两个威胁等级。**

观测手段是踩卡，不是猜高度。`lib.rs::card_contact_2027` 注释写明：卡是装在**底盘下**的 RFID 接收器，「Construction manual 3.8.2 gives a 100 mm (+/-5%) effective detection distance」，并且「**Explicit tunnel card planes prevent a robot on the roof detecting the card below it**」——顶棚上的机器人检测不到下面的卡。

引擎的判定也确实是这样（`season2027.rs:1437`）：`order=1` 的卡「lies under the roof」，只有先踩到一端（`order` 0 或 2）再踩到它，才记录 `tunnel_through`。

几何上也对得上：`configs/rules.json` 里每条隧道 3 张卡沿轴线相距 0.56-0.60m，**内侧卡半径恒为 0.17**，两端是 0.30。

**实测（真实对局，随机动作 110 步）**：

```
red-4 (2732 能变形) -> red_road_tunnel = [0, 1, 2]   ← 三张卡全踩，穿越
red-7 (2771 无变形) -> red_road_tunnel = [2]         ← 只踩到一端，跨越
```

**踩不踩得到中间那张卡，是两种过法的物理分界。** 而且这条路径在物理上是封死的：`physics.rs:674` 对 `transform_allowed=false` 的机型给的碰撞体高度是 `max(muzzle_z_m, 0.40)`，而近隧道顶棚底高只有 **0.292**（`rules.json` 的 `red_near_tunnel_roof.bottom`），非变形机型**根本挤不进去**。

### 台阶：两次 0.2m 级抬升，且不在隧道footprint内

规则 p.49 §4.3.1：「梯形高地位于制高点附近，**相对战场地面高度为 200mm**。」这解释了 SDK 里 `2731 / 2714 / 2772` 的 `step_climb_m = 0.2`。

判据是连续两帧高度各抬升 ≥0.12m、且落在 3 秒窗口内、且当时不在隧道附近。三个条件各挡掉一类误报：

- **只要一次抬升不算**：公路起伏路段是 70mm（`rules.json` 的 `road_bump_height_m`），单次抬升可能是颠簸
- **要在窗口内成对出现**：上台阶是两级，单级可能是坡
- **要远离隧道**：隧道顶棚是另一种能让高度跳这么大的人工地形（`red_far_tunnel_roof.bottom` = 0.465，`red_road_tunnel_roof.bottom` = 0.519）

### 全向：观测不到，所以留零

横向漂移在任何位置轨迹里都不留痕迹——一台车侧着平移和正着开，坐标看不出区别。所以 `is_omni` 位**恒为 0**，不填猜测。填一个猜的值比留零更糟：它会变成噪声，而策略无法验证。

## 三、为什么限定「我方视野内」

这是本方案与「直接查机型表」的关键分野。

`lib.rs:1737` 的敌方列表是 `.filter(|r| r.team != team && seen.contains_key(&r.id))`——**只有被看见的机器人才在 `obs['enemies']` 里**，而 `visible()`（`lib.rs:1642`）同时做距离判定（视野 18-20m）和遮挡射线检测。所以迭代 `obs['enemies']` 本身就是视野过滤。

卡接触数据是**全场范围**的（`zones` 的 `occupants` 不区分观察者），所以见证器把 id 映射回 slot 后，**再拿 `seen` 复核一遍**。顶棚下的机器人常常不在视线内，这让卡见证偏稀少——这是不拥有全知视角的诚实代价。

这么做的收益：策略学到的是「对手表现出来的行为」，而不是「这个机型号本来就该有的参数」。后者在训练时是作弊，泛化到只被部分观察过的对手会退化。

## 四、编码与改动点

`terrain_witness.py` 维护每槽两个 latch（一旦点亮不再熄灭），`portable.py` 的敌方段用 `witness.bits(slot)` 取这三位：

```python
if s in GROUND_SLOTS:
    values += witness.bits(s) if witness is not None else capability_bits(r)
else:
    values += [0.0, 0.0, 0.0]
```

没有 witness 时（导出后的独立提交）回退到查 `DESIGNS`——那是自包含策略在没有全场记忆时唯一能做的。这条回退是**有意的**：训练用观察，部署降级为查表。

| 位置 | 改动 |
|---|---|
| `portable.py:13-14` | `OBS_VERSION = 2`、`OBS_SIZE = 131` |
| `portable.py:19` | `GROUND_SLOTS = (1, 3, 4, 7)`，6 号空中槽不填 |
| `portable.py:56` | `encode_observation(..., witness=None)` 新增可选参数 |
| `portable.py` 敌方段 | 每槽 8 维 → 11 维：`visible + motion(5) + alive + invulnerable + traits(3)` |
| `terrain_witness.py`（新） | `TerrainWitness`：卡接触 + 台阶抬升，均限视野内 |
| `session.py:270` | `reset()` 每局新建 witness |
| `session.py:297/316/383` | 三处 obs 更新后调 `observe()` |
| `session.py:161` | `runtime_hash` 随 `portable.py` 变更 |

**不需要改引擎**：`zones` 的 occupant 与 `z` 本来就在观测里，推断全在 Python 侧。

### 20 个机型在两种模式下的分组

查表模式（无 witness）下三位是单射，4 组：

| 能力位 | 机型 | 语义 |
|---|---|---|
| `(0,0,0)` | 4, 7, 302, 2711, 2712, 2761-2763 | 普通 |
| `(0,0,1)` | 303, 2713, 2771 | 全向 |
| `(0,1,0)` | 3, 304, 305, 2731, 2714, 2772 | 轮足能上台阶 |
| `(1,0,0)` | 301, 2732, 2773 | 能变形钻隧道 |

`mecanum` 是唯一分裂成两组的 `chassis_type`（`(0,0,0)` 与 `(1,0,0)`），恰好是必须区分的那两拨——这就是不能拿 `chassis_type` 代替能力位的硬证据。

## 五、这个信号在实战里值多少

用 `guize/rmuc_2026_region_dataset.sqlite`（613 局、4,015,383 行秒级、1,474,178 条事件）量化。

### 易伤状态是高频状态

雷达标记打满后对手进入易伤。实测秒级占比：

| 机器人 | 易伤 / 总秒数 | 占比 |
|---|---|---|
| 英雄 | 111,025 / 506,788 | **21.9%** |
| 步兵4 | 103,350 / 502,229 | 20.6% |
| 工程 | 102,967 / 505,950 | 20.4% |
| 步兵3 | 100,136 / 503,436 | 19.9% |
| 哨兵 | 93,327 / 493,372 | **18.9%** |
| 前哨站 / 基地 / 空中 | 0 | 0.0% |

全体 12.7%，但剔除不可标记的建筑与空中单位后，**每台地面机器人约 20% 的存活时间处于易伤**。

### 地形增益事件是常态

2026 数据集 `事件类型='增益'` 细分：小能量机关 2,701 / 大能量机关 1,816 / 过中央高地 1,064 / **台阶跨越 1,002** / 飞坡 651。

台阶跨越分布：工程 312、步兵3 272、步兵4 240、英雄 162、哨兵 16 —— **台阶通过是常态动作**，不同机型频率差异明显，台阶能力位有真实区分度。

⚠️ **「飞坡」不能迁 2027**：规则 p.594 的赛季变更明确写「**原飞坡改为隧道**」。

## 六、A/B 验证设计

环境里天然有对照组：

| 对手 | 查表位 | 观察位 | 作用 |
|---|---|---|---|
| `dsv41_1017_pair` | `(0,0,0)` | 视行为而定 | 对照组 |
| `dsv41_1017_pair_omni` | `(0,0,1)` | 恒 `(0,0,0)` | 全向位在观察模式下失效 |

`pair` 与 `pair_omni` 同一套代码（`strategy.py` hash 均为 `f573123a3110`）只换机型。注意**观察模式下全向位恒零**，所以这一组检验的是「策略能否从别的维度补偿全向信息缺失」，而不是能力位本身。

隧道位的验证要看 `dsv41_1017_pair_s2772`（2772 轮足）与能变形的对手——若策略对钻过隧道的对手提前换防守位，说明见证器生效。

## 七、兼容性影响

`runtime_hash = sha256(portable.py)`（`session.py:161`）。改了编码器这个指纹必然变：

- **22h 旧实验（116 维）不能 `--resume`** —— `learning.py:229` 硬校验
- **不能 `--init-from`** —— 输入层 shape 不匹配
- **不能 `export`** —— `exporting.py:22`
- **`migrate.py` 走不通** —— `migrate.py:17` 要求 `obs_version == OBS_VERSION`

契约正常工作，不是回归。冒烟脚本第 2 步已显式断言这一条。

## 八、还没做的

**雷达标记（第二期）** 当前无数据源：`rules.json` 的 `excluded_systems` 排除了雷达系统，引擎不产生 `RadarInfoToClient`。要做须先补引擎侧的识别与标记进度 P，再升 `OBS_VERSION`。

**「都不能」这一类的显式编码**：目前 `(0,0,0)` 同时表示「观察到它没做任何地形动作」和「还没观察到」。两者在训练早期无法区分。若要区分，需要三态（未知/能做/不能做）而非二值 flag，那会把每槽从 3 维扩到 6 维。当前判断不值得——未见过的对手本来就该按默认处理。

## 九、这个观测到底在服务什么：动作空间是 2 维

这一条决定了后面所有「该不该给 RL 加某个观测」的判断，所以单列。

`env.py:21` 的动作空间是 `gym.spaces.Box(-1, 1, shape=(2,))`，两个分量是**归一化的地图落点 (x, y)**。瞄准、开火、姿态切换、买弹、复活路径，全部由
`examples/claude_opus55_xhigh_2027_squad/robot_7.py` 里的 `baseline.weapon()` 决定，RL 不碰。

推论：

1. **RL 训练的是「哨兵导航器」，不是完整哨兵策略。** 它只能回答「下一拍往哪走」，不能回答「打不打」「用不用攻击姿态」。所以把姿态/弹药相关的奖励权重设成 0 **不是缺陷**——那些动作本来就不在 RL 的动作空间里，给它们付奖励等于给一个无法执行的动作发放报酬，梯度噪声只增不减。
2. **任何「让观测更接近人类视角」的扩容，都要先问新维度能不能改变落点选择。** 敌方的隧道/台阶能力位能改变（绕后路线不同），所以值得编码；敌方剩余血量百分比也能改变（打残了要不要压），已经编码。但「敌方当前是攻击姿态」对落点几乎没有作用面，加进去只是增加输入噪声。
3. **`terrain_buff` 奖励的稀疏性是这个结构的直接后果。** 默认编队 slot 7 是 2771（omni，不可折叠），物理上进不了隧道；换成可折叠的 2773 后，实测 140 秒全零动作里 `terrain_buff` 事件 0 次、导航器还会把目标重映射到 (14.25, 13.5) 并卡在 (9.1, 12.0)。这不是奖励写错了，是「让一个 2 维导航器去踩地形卡」本身就很难被随机探索命中。要让这个信号有用，得先解决导航器能不能到达，而不是加大权重。

## 十、本轮顺带修掉的两处自相矛盾

| 位置 | 原来 | 现在 |
|---|---|---|
| `control` 归一化 | 硬编码 `/1680`，而实测红方全场峰值 863，特征终生在量程下半段 | 配置项 `control_scale`，默认 1000；导出时写进 `_CONFIG` 和 `experiment.json` 的 `observation` |
| 胜负判据 | `session.py` 算符号、`learning.evaluate` 另写一套 win/draw/loss | 同源 `result_sign` / `result_label`，`evaluate` 的 `sim_backend` 跟随训练配置 |

两处都不改观测维度，所以 `OBS_VERSION` 仍为 2。但 `control_scale` 会进入 `experiment.json`，续训/评估/导出会核对它——这是有意的：改了它就等于换了输入尺度。
